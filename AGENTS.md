# AGENTS.md

Правила работы в этом репозитории для AI-агентов (Claude Code и прочих).

## Что это за проект

Исследование: помогает ли вмешательство в активации (steering) агенту правильно менять план
по смыслу полученного результата инструмента, и выгоднее ли это промпта, явного ведения
состояния и дообучения.

Перед работой прочитать: [CONTEXT.md](CONTEXT.md) → [docs/JOURNAL.md](docs/JOURNAL.md) (что уже
сделано и решено) → [docs/HYPOTHESES.md](docs/HYPOTHESES.md) → [docs/METRICS.md](docs/METRICS.md) →
[docs/PIPELINE.md](docs/PIPELINE.md) (как запускать эксперименты).

## Главные правила

1. **Гипотезы и метрики зафиксированы.** `docs/HYPOTHESES.md` и `docs/METRICS.md` менять только
   явным решением человека, с отметкой даты и причины в самом файле. Не «улучшать» их по ходу
   прогонов — это превращает подтверждающий результат в разведочный.

2. **Не трогать финальный test.** Он открывается один раз, после заморозки метода и baseline.
   Любой подбор гиперпараметров, слоя, `α`, окна и промпта — **только на validation**.

3. **Чувствительность и специфичность отчитываются вместе.** Никогда порознь. Метод, поднявший
   переключения на меняющих парах за счёт инвариантных, ничего не улучшил.

4. **Рост частоты смены действия — не улучшение.** Это самая вероятная ошибка интерпретации
   в этом проекте.

5. **Одинаковые данные для обучаемых методов.** Иначе сравнение не про способ вмешательства.

6. **Разведочные находки помечать как разведочные** и подтверждать на отложенной выборке.

7. **Воспроизводимость.** Любой прогон пишет в `results/runs/<run_id>/` манифест: модель,
   хеш chat template, формат вызова, параметры решения, seed, хеш данных, git commit и
   незакоммиченные файлы. Это делает `Experiment` — прогон в обход него считается несуществующим.

8. **Вся история — в `docs/JOURNAL.md`.** Каждый содержательный прогон заканчивается
   `exp.report(conclusion=..., next_step=...)`; решения и идеи — `stf-note`. Старые записи
   не редактировать: ошибка исправляется новой записью со ссылкой на старую.

## Эксперименты — только через пайплайн

- Новый эксперимент — копия `notebooks/00_TEMPLATE.ipynb`; меняется ячейка конфига.
  Логику в ноутбук не писать: если не хватает стадии, метода, метрики — добавить её в
  `src/` с тестом (как — `docs/PIPELINE.md`, «Как расширять»), чтобы она работала для всех прогонов.
- Не обходить защиты: не ловить `TestLockError`/`StageOrderError`, не вызывать бэкенд
  напрямую для оценки на test, не чистить `results/test_lock.jsonl`. Повторное открытие
  test — только через `eval.reopen_test_reason`, и это остаётся в журнале.
- Перед реальной моделью: `01_smoke_mock` и `02_model_check` (окна глазами, хук, оценка
  времени). После правок в `src/` — `pytest`.
- Вердикты `gates.py` — подсказка по правилам HYPOTHESES.md, не вывод. Не менять пороги
  гейтов под конкретный результат.
- Флаги в отчёте («грязный git», «изменены HYPOTHESES/METRICS», «mock», «test открыт
  повторно») не скрывать и не обходить — их наличие пишется в журнал.
- Коммитить ноутбук **с выводами** вместе с записью в журнале — это запись лабораторной
  работы. `results/` (кроме index, test_lock, frozen, protocol) остаётся локально.

## Границы метода

- Веса базовой модели **не меняются** в основной версии метода.
- Вмешательство только после ответа инструмента, в выбранном окне.
- Гейт не использует oracle-метку, контрфактическую ветку и будущую траекторию.
- Агенту в прогоне недоступны: парный результат, gold, будущие шаги, verifier.
- Нельзя подставлять patching-ом сам ответ инструмента или готовое действие.

## Код

**Установка и импорт.** Код — пакет `steering_tool_feedback` в `src/`. Ставить
`python3 -m pip install -e ".[model,notebooks,dev]"` в тот интерпретатор, которым запускаешь.
Импорт только как пакет (`from steering_tool_feedback import metrics`); никаких
`sys.path.insert`. Если «модуль не найден» — сначала `stf-doctor`.

**Тесты.** `pytest` перед любым коммитом в `src/`. С реальным шаблоном:
`STF_TOKENIZER=<папка токенизатора> pytest`. Новый код хуков или окон без теста
не принимается.

**Окна позиций — обязательная проверка глазами.** На каждой новой модели или новом
chat template до первого прогона: `stf-windows --tokenizer <...>` и `--all`.
Окна строит только `windows.prepare_prompt` (по offsets токенов в отрендеренном тексте).
Не считать окна арифметикой длин: на шаблоне Qwen3.x это клало `post_message`
в generation prompt, не задевая ни одного токена ответа инструмента.
В модель подавать **только** `PreparedPrompt.input_ids` / `.model_inputs()` —
тогда окна и вход не разъедутся.

Пять окон: `tool_content` (текст ответа), `field_read` (ключ+значение существенного поля),
`post_message` (хвост ответа + закрывающая обёртка шаблона), `pre_action` (generation prompt),
`action_point` (последний токен промпта — точка выбора действия; окно адаптации TACT).

**Хуки.** После каждого прогона со steering проверять `hook.n_applied == len(window)`
(0 = окно мимо; «нулевой эффект» тогда ничего не значит) и
`hook.positions_source != "counter"` (позиции должны приходить из модели).

**Ограничения и ловушки.**
- batch = 1 для съёма активаций и steering — хук бросает ошибку на batch > 1.
- Qwen3.x открывает ответ блоком `<think>`: `pre_action` — момент перед рассуждением,
  а не перед вызовом. Парсер действия должен пропускать `<think>…</think>`.
- Словарь Qwen3.x 248k: полные логиты на ~1k токенов ≈ 1 ГБ fp32. Для выбора действия
  брать `logits_to_keep=1` или генерацию, для сравнения состояний — скрытые состояния.
- Шаблоны меняют промпт сами (шаблон LM Studio для Qwen3.8 дописывает в system
  «Reasoning effort is set to xhigh…»). Хеш шаблона — в манифест прогона.

**Остальное.**
- Результаты — в `results/`, данные — в `data/`.
- Сырые активации и большие дампы не коммитить (см. `.gitignore`), хранить путь и хеш.
- Детерминированность по умолчанию: фиксированный seed, зафиксированный decoding.
- Любой новый baseline добавлять в тот же scaffold, а не отдельным скриптом со своей обвязкой.
