## 2026-09-24 · ретроспектива · постановка и проверка ниши

**Риск метода.** Явное ведение состояния (OODA-подобный контроллер) может дать то же
качество дешевле — оценка риска ~40%. Steering как «главный вклад» уязвим.

**Отвергнутые рамки:**
- ось «отзывчивость ↔ манипулируемость» (safety, tool-injection) — слишком сложно,
  требовало бы трёх отдельных статей;
- «как инструкция из промпта доходит до выбора действия» — ниша занята:
  2410.14516 (внутренняя размерность следования инструкциям + интервенция, single-turn)
  и 2410.12877 (steering ради instruction-following, ICLR 2025).

**Принято.** Центр новизны — парный протокол: одинаковая история и вызов, меняется
только правдивый ответ инструмента → должно ли смениться действие. Steering —
инструмент проверки, а не самоцель. Проверено по абстрактам и HTML, полные тексты
ключевых работ ещё не прочитаны.

## 2026-10-02 · ретроспектива · правка Ивана, постановка одобрена

Вопрос «есть ли правильное действие в активациях» слишком широкий → три проверки:
1. различает ли модель ответы (probe);
2. использует ли это различие без вмешательства;
3. чинит ли сбой steering, не портя случаи, где план менять не надо.

Пункт 1 не гарантирует пункт 3. Если информации в активациях нет — помогает не только
дообучение: явная запись состояния, разбор ответа, сильный промпт. Иван: «постановка
хорошая, давай реализовывать».

   доступа) ∧ нет нарушений (заказ отсутствующего/не того товара, proceed без доступа) ∧
   ≤ 4 решений. Аргументы пишет модель. Вмешательства работают на каждом шаге.
3. **Методы.** `explicit_state` (OODA-состояние пишет сама модель — обвязка не знает, какое поле
   существенно), `steering_gated` (гейт = логрегрессия на активациях окна, train; порог на val),

4. **Вердикты.** H3 теперь требует и прирост успеха эпизода, если эпизоды оценивались

   до этого эпизод = одно решение, и требование выполнялось тождественно. H4 — steering vs

5. **Test-lock.** freeze_id покрывает весь выбранный набор методов; открытие test той же
   модели и данных под другим freeze_id не блокируется, но помечается флагом в журнале.
6. **Окружение.** Системный python3 на Mac — 3.9 (проекту нужен ≥ 3.10): `.venv` через uv,

## 2026-10-19 20:29 · баг

**Баг скоринга действий найден на первой обученной модели и исправлен до прогонов.**
`02_model_check` на Qwen3-1.7B (MPS, fp16): log-prob лучшего действия ≈ −37…−40 nats, хотя
первый токен имени (`request`) модель ставит с вероятностью ≈ 1. Причина: скорер дописывал
к имени отдельный токен закрывающей кавычки `"`, а Qwen3 всегда пишет слитный `",` — одиночный
`"` стоил десятки nats и **по-разному для разных действий**. Артефакт переворачивал решения:
в ветке «доступ есть» выигрывал `ask_user` (−40.2) вместо `proceed`.

Исправление (`actions.name_tokens`): токены имени берутся из канонической токенизации
отрендеренного вызова (префикс + имя + остаток вызова) — ровно то, что модель пишет сама;
проверяется, что префикс одинаков для всех действий и ни одно имя не префикс другого.
После исправления: у выбранного действия log-prob ≈ 0, общий KV-кэш = полный прогон
(|Δ| < 1e-4), на 6 пробных промптах все решения верны, модель сама пишет аргументы
(`{"item": "phone case"}`, `{"doc_id": "DOC-553"}`). Регрессионный тест — на реальном
шаблоне (`test_scored_tokens_are_canonical_real`). Тесты на случайных весах этого поймать
не могли: на них все log-prob одинаково плохие.

Наблюдение (не результат): на 6 пробных промптах модель уверенна (отрыв ≥ 2 nats) и права —
риск «H2 против» (ошибок мало) реальный. Правило из HYPOTHESES на этот случай — менять
постановку задач, а не метод.

## 2026-10-19 20:46 · решение

**Контроль shortcut в H1 был пустым — исправляю до того, как увидел probe на реальной модели.**
Записываю, пока черновой прогон 03 считает базу: таблицы probe ещё не видел.

`probe.run_probe` для shortcut-теста обучал **новый** классификатор отличать компактный JSON от
развёрнутого на инвариантных парах. На настоящей модели формы различимы всегда (это разные
токены), так что `suspected_shortcut` срабатывал бы на каждом (слой, окно), и H1 никогда не
могла бы получить «support» — контроль ничего не проверял. По смыслу (docstring probe.py:
«probe уверенно отличает ИНВАРИАНТНЫЕ ветки → читает форму, не смысл») проверять нужно
**тот же probe состояния**: обучить его на меняющих парах и применить к инвариантным, где
состояние одно («нет в наличии»), а форма разная.

Новое определение (порог 0.65 прежний): `shortcut_auroc` = AUROC, с которым оценка probe
состояния разделяет две формы инвариантной пары (0.5 = форма не влияет); дополнительно
пишется `invariant_transfer` — доля инвариантных веток, которые probe относит к верному
состоянию. Порог и правило гейта h1 не меняются.

## 2026-10-19 21:08 · решение

**Постановка v3 (`data.generator = "v3"`, по умолчанию с этого момента).** Решение по правилу
HYPOTHESES «H2 не подтвердилась → менять постановку задач», принято после аудита ошибок v2 и
разведочного пилота (seed 1000, вне данных v3); на данных v3 модель ещё не запускалась.

Суть: ответ check_stock всегда содержит все поля (наличие, количество, срок доставки, цена), а что
из них существенно — задаёт запрос пользователя. Меняющие пары: «подходит» → place_order;
«не подходит» → альтернатива. Типы: наличие (14%), срок доставки (20%), количество (12%),
бюджет (8%), доступ к документу (10%); инвариантные — 30% (форма: развёрнутый JSON / проза;
нерелевантное поле: меняется то, что этот запрос не ограничивает), стресс — 6%. В каталоге

**Методы добавки в активации — устройство до первого прогона** (по итогам 07). Все четыре — поправка
в одной позиции одного слоя: точка вызова = последний токен перед именем действия (промпт + префикс вызова).
Данные — те же, что у вектора и LoRA: меняющие пары train (110 промптов). Выбор — на val общим правилом;
проверка — на НОВОМ наборе переноса (seed 202; набор seed 101 уже использован).

- `linmap_lora` — аффинная поправка h ← h + α·(h·U·P + a0), подогнанная в закрытой форме
  (стандартизация → PCA 32 → ridge → ранг r) к Δh = h_LoRA − h_база. LoRA — учитель: обучение нужно один раз
  (для LoRA), при работе веса не меняются. Сетка: слои {16..26 через 2}, ранг {4, 8, 16}, α {0.5, 1, 1.5}.
- `linmap` — то же **без учителя**: цель для неверного решения базы — центроид верных состояний с тем же
  правильным действием, для верного — ноль. Без градиентного обучения вообще — это и есть цель этапа.
- `reft` — LoReFT (Wu et al., 2404.03592, формула сверена по тексту): h + Rᵀ(W h + b − R h), R с
  ортонормированными строками; обучается градиентом только вмешательство (ранг 4, 3 эпохи, lr 2e-3), веса
  модели заморожены; слои {18, 22, 26}. При работе — та же аффинная форма. Это потолок «вмешательства в
  одну точку», а не «без обучения».
- `cast` — CAST (Lee et al., 2409.05907, сверено по тексту): вектор условия — PC1 центрированного контраста
  «не подходит / подходит» в последнем токене промпта, проверка sim(h, tanh(proj_c h)) против θ; слой, θ и
  направление — по F1 на train. Вектор поведения — PC1 контраста «база не заказала / заказала» в окне
  generation prompt; слой {16, 20, 24} и сила {0.5, 1, 2} — на val. Замечание: sim из CAST знаковонезависима
  (меряет выравнивание с c, а не сторону).

**SimplexLoRA** (Shalygin et al., 2610.37206, МФТИ, Findings EMNLP 2026; прочитано по HTML): важность
адаптеров — веса ω на масштабированном симплексе (Σω = n), учатся в короткой разминке (K·T ≈ 50 шагов,
регуляризация ‖ω − 1‖²), затем ранги r_i = ⌊r_0·ω_i⌋ при неизменном бюджете; у DeBERTa больше ранга получают
value-проекции; выигрыш — на малых рангах. Лицензия кода в репозитории не указана — код не берём, только идеи.
Что переносится к нам: (1) распределять бюджет вмешательства (ранг, силу) по нескольким слоям по
важности на симплексе вместо одного слоя; (2) важность без обучения у нас уже измерена — кривая подстановки
из 07 (с учителем) или качество закрытой подгонки по слоям (без учителя); (3) для самой LoRA — сравнить
равномерный ранг с распределением по важности. Это следующий шаг после одноточечных методов.
