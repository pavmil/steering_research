# Пайплайн экспериментов: как устроен

Цель системы — чтобы новый эксперимент был **копией ноутбука с другой ячейкой
конфига**, а всё остальное (данные, кэш, протокол, метрики, отчёт, журнал)
работало одинаково для всех прогонов и не давало случайно нарушить протокол.

## Как запустить эксперимент

```text
cp notebooks/00_TEMPLATE.ipynb notebooks/05_my_idea.ipynb
# в ноутбуке поменять только ячейку cfg = ExperimentConfig.make(...)
# запустить сверху вниз; в последней ячейке вписать вывод
```

| Ноутбук | Когда |
|---|---|
| `01_smoke_mock` | после установки и после правок в `src/` — вся обвязка за секунды, без модели |
| `02_model_check` | один раз на новую модель/шаблон: окна глазами, формат вызова, хук, оценка времени |
| `03_h1_h2_baseline` | H1 + H2 на постановке v2 (явный смысл ответа) — выполнен, см. JOURNAL |
| `05_h1_h2_v3` | H1 + H2 на постановке v3 (смысл ответа относительно цели пользователя) |
| `04_h3_steering` | H3 + сравнение со всеми методами (промпт, пересказ, явное состояние, гейт, TACT, LoRA), sham-контроли, эпизоды; test один раз |
| `00_TEMPLATE` | заготовка для всего остального |

Без Jupyter: `stf-run --config configs/qwen3-1.7b-mac.yaml --until probe`.

## Стадии

```text
 ExperimentConfig ──► Experiment(cfg)
                         │
   data ─────────────────┤  задачи → аудит → разбиение по задачам (без утечки содержимого)
   baseline   train+val ─┤  решения базы: материал для H2 и для контраста вектора
   probe      train ─────┤  H1: probe по (слой × окно), CV по задачам, перестановка, shortcut
   vectors    train ─────┤  CAA: верные vs неверные решения базы на меняющих парах
   sweep      val ───────┤  слой × окно × alpha → выбор: max успех при Δспецифичности ≤ допуска
   fit   train → val ────┤  гейт, TACT, LoRA: обучение на train, выбор на val тем же правилом;
                         │  все методы на val (+ эпизоды) — картина до test
   freeze ───────────────┤  весь выбранный набор методов → results/frozen/<freeze_id>
   test       test ──────┤  ОДИН раз: база, все методы, 4 sham-контроля, эпизоды, метод-vs-метод
   report ───────────────┘  вердикты H1–H4 и ALT → report.md, results/index.csv, docs/JOURNAL.md
```

`exp.run(until="sweep")` выполняет стадии по порядку и пропускает сделанные.
Стадию нельзя вызвать раньше предыдущих — `StageOrderError`.

## Компоненты

| Модуль | Ответственность |
|---|---|
| `config.py` | Один датакласс на весь прогон; переопределения точками (`"steer.alphas"`); хеш вычислений |
| `simulator.py` | Парные миры, инварианты протокола, генератор уникальных задач (v2: поздняя позиция с настоящей историей), разбиение |
| `episodes.py` | Многошаговая среда от точки решения пары: правила мира, verifier, `rollout` |
| `windows.py` | Окна позиций по offsets токенов в отрендеренном шаблоне + печать токенов |
| `actions.py` | Формат вызова инструмента из шаблона модели; разбор действия из текста |
| `backends/` | `HFBackend` (CPU / MPS / CUDA) и `MockBackend` — один интерфейс |
| `methods.py` | Реестр методов: baseline, strong_prompt, restate, explicit_state, steering, steering_gated, tact, lora, sham:* |
| `steering.py` | Хуки (CAA, проекция TACT), векторы и оси дрейфа, sham-векторы |
| `finetune.py` | LoRA/SFT на тех же данных (копия модели; оценочная модель не меняется) |
| `probe.py`, `metrics.py` | H1-probe с контролями; метрики из METRICS.md |
| `pipeline.py` | Стадии, кэш, протокол, сводки |
| `gates.py` | Вердикты по правилам HYPOTHESES.md + ALT (условие провала тезиса из CONTEXT §3) |
| `store.py`, `journal.py` | Файлы прогонов, кэши, index.csv; журнал исследования |
| `viz.py` | Графики для ноутбуков |

## Методы

| метод | как устроен | данные / подбор |
|---|---|---|
| `baseline` | без вмешательства | — |
| `strong_prompt` | инструкция учитывать ответ — в system | текст фиксирован |
| `restate` | модель пересказывает ответ (≤48 ток.), затем действует; 2 вызова | — |
| `explicit_state` | OODA: модель пишет GOAL / OBSERVED / PLAN STILL VALID / NEXT STEP (≤96 ток.), затем действует; состояние пишет модель, а не обвязка | — |
| `steering` | CAA-вектор `h += α·‖h‖·v̂` в окне после ответа, всегда включён | вектор — train, (слой, окно, α) — val |
| `steering_gated` | тот же вектор, но только если гейт (логистическая регрессия на активациях окна) предсказывает ошибку базы. Решение собирается из кэша steering/базы — ровно то, что дал бы однопроходный хук с гейтом | гейт — train (меняющие + инвариантные), (вектор, α, порог) — val |
| `tact` | адаптация TACT-Gate (2605.05980): ось «верно → сбой» по задачам, в точке действия (`action_point`) на top-K слоях; сдвиг только вне полосы k·σ | оси — train, слои по AUC и λ — val, k = 2 как в статье |
| `lora` | LoRA r=8 на q/k/v/o, SFT на верный вызов; адаптер включается только на время решения | те же меняющие пары train, (lr, эпохи) — val |

Отличия адаптации TACT от статьи: одна ось (overacting vs calibrated) — оси overthinking
нет, потому что решение принимается без рассуждения; метки — правильность решения базы
по правилам среды, а не LLM-судья; точка — последний токен промпта (у Qwen3 без
рассуждения — сразу после `</think>`), а не `</think>` после реального рассуждения.

## Многошаговые эпизоды

`episodes.py`. Эпизод начинается в точке решения пары, поэтому **первое решение эпизода —
то же одношаговое решение** (тот же промпт, тот же кэш). Дальше среда исполняет действия
агента по правилам мира ветки и возвращает правдивые ответы:

- магазин: `search_alternative` → список альтернатив (видны только так) → `place_order`
  альтернативы или `ask_user`; заказ отсутствующего или не того товара — нарушение;
- документы: `request_access` → владелец одобряет → `proceed`; `proceed` без доступа — нарушение.

Успех эпизода = первое решение в A* ∧ цель достигнута ∧ нет нарушений ∧ ≤ `episode.max_steps`
решений. Аргументы вызова пишет модель (жадно, после выбранного имени); среда их не
исправляет. Вмешательства методов работают на каждом шаге (после каждого ответа
инструмента) — как при развёртывании. Стресс-пары оцениваются только одношагово.

## Данные: версии генератора

`data.generator` (по умолчанию `v3`). Версия пишется в манифест и в `data.json`.

| версия | что меняется в паре | зачем |
|---|---|---|
| `v2` | явный смысл: `in_stock` true/false, доступ granted/denied | первая постановка; на Qwen3-1.7B ошибок почти нет (03) |
| `v3` | ответ содержит все поля (наличие, количество, срок, цена); существенное задаёт запрос пользователя — «в наличии», но позже срока / меньше нужного / дороже бюджета | целевой сбой: ключевое слово тянет к неверному действию |

В v3 A* «плохой» ветки зависит от явности условия (явное — только предписанное действие,
неявное — ещё `ask_user`), инвариантные пары обеих полярностей и трёх видов: форма
(развёрнутый JSON / проза), длина, нерелевантное поле. В каталоге альтернатив в половине
задач первой идёт неподходящая.

«Поздняя» позиция критического ответа (ось из EXPERIMENT_PLAN) — настоящая: до
критического вызова в истории уже есть полный цикл по другому товару (проверка → заказ)
или документу. История одинакова в обеих ветках.

## Как принимается решение о действии

**scored** (по умолчанию). Промпт → префикс вызова инструмента, выведенный из
шаблона модели (`<tool_call>\n<function=` у Qwen3.5, `<tool_call>\n{"name": "` у
Qwen3/2.5) → log-prob имени каждого из 9 действий. Prefill промпта один,
продолжения считаются из общего KV-кэша (проверено: совпадает с полным прогоном
до 5·10⁻⁶). Детерминированно, быстро, без рассуждения — основной режим для подбора.

**generate**. Обычная генерация (рассуждение — если `model.enable_thinking=True`),
действие — `parse_action` (вызов после `</think>`; незакрытое рассуждение — `unparsed`).
Медленно, для финальной проверки, что вывод не артефакт скоринга.

**Аргументы** (только в эпизодах): после выбранного имени модель жадно дописывает
аргументы вызова до `</tool_call>`; разбирает `parse_arguments` (JSON или XML-форма Qwen3.5).

Токенизация при скоринге (проверено на Qwen3-1.7B): префикс заканчивается на ` "`,
поэтому токены имени действия совпадают с канонической токенизацией полного вызова;
отличается только закрывающая кавычка (`"` вместо `",`).

## Что гарантирует протокол (и где это проверяется)

| Правило | Механизм |
|---|---|
| Вектор, гейт, оси TACT, LoRA — только из train | `vectors()`/`fit()` берут только train; `provenance.split = "train"` |
| Подбор только на val, одним правилом | `sweep()`/`fit()` оценивают только val; `_select`: max успех при Δспецифичности ≤ допуска; test-решения до freeze не создаются |
| Одинаковые данные для обучаемых методов | LoRA учится на тех же меняющих парах train, что и вектор (тест проверяет число примеров) |
| Test один раз | `results/test_lock.jsonl`; повтор → `TestLockError`; с `eval.reopen_test_reason` — проходит, но флаг в журнале |
| Новый набор методов на тех же данных — тоже видно | открытие test той же модели и данных под другим `freeze_id` → флаг в журнале |
| Обойти lock сменой «неважного» параметра нельзя | `freeze_id` = модель + данные + выбранные параметры ВСЕХ методов + режим решения (+ эпизод), без прочего конфига |
| Хук попал в окно | каждое решение со steering/TACT проверяет `n_applied == len(окно)` (TACT — на каждом слое); позиции из модели, иначе флаг |
| LoRA не загрязняет базу | адаптер включается в контексте решения и выключается в `finally`; решение базы при включённом адаптере — ошибка |
| Нет утечки между сплитами | одинаковое содержимое задач в разных сплитах → ошибка |
| Чувствительность не без специфичности | `target_effect` отказывается считать одно без другого |
| Видно, если протокол менялся | хеши HYPOTHESES.md / METRICS.md в манифесте и флаг при расхождении с первым прогоном |
| Прогон воспроизводим | manifest: git-коммит, «грязные» файлы, версии, хеш шаблона, формат вызова |

## Кэш

Ключ решения = модель (+dtype, устройство, хеш шаблона) + fingerprint метода
(вариант промпта, вектор, слой, окно, alpha) + хеш токенов промпта + режим решения.
Активации — по хешу токенов промпта, массивы по (слой, окно).

Следствие: ноутбук 04 после 03 не пересчитывает базу и активации; правка alpha
пересчитывает только новые alpha. Кэш лежит в `results/cache/<модель>/` и
переживает прогоны. Удалить его безопасно — всё пересчитается.

## Где что лежит

```text
results/                      локально; в git только index.csv, test_lock.jsonl, frozen/*.json, protocol.json
  index.csv                   все прогоны одной таблицей
  runs/<run_id>/              config.yaml, manifest.json, decisions/*.jsonl, probe.csv,
                              sweep.csv, selection.json, test.json, report.md, log.txt
  cache/<model>/              decisions.jsonl, acts/*.npz, lora/<adapter_id>/ (адаптер + train_info.json)
  frozen/<freeze_id>.json     замороженные методы (+ .npz вектора)
docs/JOURNAL.md               история исследования — в git
```

## Как расширять

| Хочу | Что поменять |
|---|---|
| Новый метод-сравнение | запись в `methods.METHODS` + ветка в `build_messages` (если меняется контекст) |
| Новый sham-контроль | `config.SHAMS` + ветка в `Experiment._sham_specs` |
| Новый обучаемый метод | запись в `METHODS` с `fitted=True` + `Experiment._fit_<имя>` (train → строки val → `_select`) + ветка в `_specs_for` и `freeze` |
| Новый домен задач | генератор пар в `simulator.py` + шаблоны в `_REQUESTS`; аудит проверит инварианты |
| Новое окно | `windows.prepare_prompt` + `config.WINDOW_KINDS` |
| Новая метрика | `metrics.py` + поле в `Experiment.summarize` |
| Новый гейт | `gates.py` — по правилам из HYPOTHESES.md, а не под конкретный прогон |

## Mac (Apple Silicon)

- Устройство и тип выбираются сами: `mps` + `float16`; неподдержанные операции
  уходят на CPU (`PYTORCH_ENABLE_MPS_FALLBACK=1`).
- Модели 1–3B в HF-формате: `Qwen/Qwen3-1.7B` (по умолчанию в ноутбуках),
  `Qwen/Qwen2.5-1.5B-Instruct`, `meta-llama/Llama-3.2-3B-Instruct` (нужен доступ на HF).
  Гибриды с линейным вниманием (Qwen3.5/3.6) на MPS идут через медленную
  референсную реализацию — для пилота не брать.
- MLX-модели из LM Studio transformers не грузит. Их токенизатор годится только для
  `stf-windows`.
- `exp.estimate()` до запуска: sweep — самая дорогая стадия
  (слои × окна × alpha × val). Уменьшать `steer.top_k_layers`, `steer.windows`, `steer.alphas`.
- Батч = 1 (ограничение хуков и окон).

## Что пока не сделано

- **Глобальный срез для H4.** H4 сравнивает steering и LoRA на условном (парном) срезе;
  глобальный срез («общее улучшение формата/стиля действий») не определён — без него
  вердикт H4 не может быть «support». Нужно решение Павла (см. JOURNAL).
- **PRISMS** — не адаптирован (только на пересекающемся срезе ошибок вызова).
- **Окно внутри рассуждения.** Для `enable_thinking=True` окно «перед первым токеном вызова
  внутри генерации» не реализовано; `pre_action`/`action_point` стоят перед рассуждением.
- **Внешняя среда** (ToolRobustBench + одна многошаговая) — не подключена.
- Сверка `scored` с `generate` на финальной проверке — не сделана.
